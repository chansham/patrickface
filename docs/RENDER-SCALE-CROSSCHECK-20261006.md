# 2026-10-06 角色尺度：Web／原生獨立交叉核對

本報告按 2026-10-06 最新 catalog／版式重新量測，讀取程式、原圖、輪廓 sidecar 與既有 Apple simulator PNG。這份量測沒有改 PNG、catalog、倍率或 bundle；另依本輪任務，在原生 DEBUG simulator 與截圖工具加入純診斷 probe，尚待 Apple 執行，未改渲染幾何。

## 結論

- 同一內容舞台內，Web 與 Swift 的輪廓來源順序、固定畫布、clip.scale、落位基線錨點及版式 transform 數學一致。實際執行 JS 與獨立轉錄的 Swift 計算，共 348 個矩形比較，最大座標差 1.14e-13 px（浮點尾差）。這不是重新執行 SwiftUI。
- 15 個主目錄播放變體、14 個候選變體，共 324 個有序播放位置已核對。重複眨眼／主候選共用原圖不算新原畫。全部 4 版式的 alpha≥128 全輪廓未超出完整矩形舞台；這不表示本體大小一致、未遮數字或通過圓角裁切。
- 兩端原生主 catalog、所有主目錄 PNG/regions、layouts.json 目前逐 bytes 相同。**本輪新倍率與版式已同步兩端，逐 bytes 核對通過；但尚須重建並取得新 probe。之後若再調倍率或 sidecar，兩端都必須重新同步、SHA驗證、重建。**候選不是原生運行目錄，不應把候選直接導入當批准。
- 大部分 clip.scale 恰好是 N／舊格最長邊，用來抵消輪廓畫布留白；exercise 多乘 1.4。本輪 celebrate／派對全段再乘 1.30，charging／太空充電全段乘 1.10，主／候選一致；activity 資訊欄 x=476。其餘沒有逐格縮放。這些數值與輪廓尺寸不能單獨證明不同服裝本體等大，仍需語義 landmark 與肉眼核对。

## 計算鏈

1. 輪廓 run 選出原 PNG 像素；Web 以整數 translation 畫到 N×N，Swift CGContext 同樣以整數 translation 畫到 N×N，只轉換一次 Y 方向。两端均用 frameIndices 選來源格；没有時依 0..<frameCount。
2. 在 832×992 內容舞台，角色區起點 (83.2,248)、邊長 665.6；master anchor=(0.5,0.97)，故共同落位目標 T=(416,893.632)。輪廓畫布 anchorPixels=(Ax,Ay) 是落位基線；太空與廚師造型包含坐墊，不能解讀成人物真足底。源像素 q 經平移到 p 後，畫面座標 = T + (p−A) × 665.6 × clip.scale/N。
3. 版式 (k,dx,dy) 對整段套 k×座標+(dx,dy)，再乘 u=min(可用寬/832,可用高/992)。完整416×496內容舞台 u=0.5；200px寬腕上示意 u=200/832；iPhone 300pt內容舞台 u=300/832。不能把點(pt)、CSS px和設備物理像素混為一談。
4. Swift Image 的 .position 給的是中心。減去 frame寬高/2後，與 Web destinationRect 的左上角完全一致；沒有多除一次 cell、額外逐格 fit 或把 N 當人物本體。

## 具體例子與原生實圖界線

- 哈欠 yawn：N=652、舊格443.5px、scale=652/443.5=1.470124。完整416舞台每來源像素呈0.750395px；帽子／枕頭全輪廓高309.2–319.7px。改N而同步按N增加scale，人物可見大小不變。
- 運動 exercise：N=728、舊格最長邊384px、scale=(728/384)×1.4=2.654167。每來源像素在416舞台呈1.213333px；全輪廓高287.6–292.4px。新落位基線 sidecar未被原生遗漏，兩端相同。啞鈴會影響總寬，不能以總寬證明臉大小一致。
- 偵探帽候選：N=812、舊格362px、scale=812/362=2.243094；全輪廓高304.3–308.9px。帽頂增加總高卻不等於頭部本身大。廚師帽 feed 的總高316.1–318.5px看似接近哈欠，但臉／身體仍需獨立 landmark。
- 新倍率：celebrate 的 clip.scale=2.830208，416完整舞台全輪廓高281.7–286.2px；太空 charging 的 clip.scale=2.309487，全輪廓高313.4–321.1px。這是整段同倍率，不是改每格人物大小。activity 資訊欄由x450移到476，角色transform仍[0.56,8,354]。
- 144×144px逐格縮圖現已使用同一經典832×992舞台：`factor=144/992`、`insetX=(144−832×factor)/2`，再套真正的`destinationRect`（包含clip.scale）。這保留造型之間的舞台比例，沒有再按各自N畫布fit。`preview/test-regions-browser.cjs:146`已加入對應矩形回歸驗證。縮圖可比較共同舞台的呈現，仍不能把帽子／坐墊／道具總高當人物本體尺寸。

已讀取 run37400000919 的真實416×496 Watch截图。RGB色差門檻測得 yawn 彩色外框：classic 168×204px、bold 115×141px、theater 159×194px、activity 93×114px。後三者分別接近 classic×0.69／0.95／0.56，與版式契約相符。classic同來源顏色門檻按完整416內容舞台計應約261.1×319.7px，截圖約為其0.64倍。

**416×496整張原生PNG ≠ 416×496內容舞台。** Watch外層先把416:496舞台fit進系統提供的安全GeometryReader，內層再以832×992座標畫；黑背景延伸到安全區，但角色不延伸。上述截圖可反推有效舞台寬約267px，不能單憑PNG確定具體safeAreaInsets或點數。本輪已加僅 DEBUG simulator 的 probe，下一次 Apple QA 將記錄Geometry尺寸、safeAreaInsets、screenScale、實際前景／腕下狀態。`--watch-geometry` 會核對本次程序、版式與時間；尚未取得新值，不能將上述反推值當實測。取得後再把Web模擬器設成同一可用區；不應為追平完整Web舞台而任意把某些clip放大，否則會混淆平台可用区與角色比例。

## 護欄與下一步

- 當前29變體全部滿足原生scale 0.1…4、每幀16…30000ms、全段≤120000ms的限制。Web只要求scale為正有限值，未共用上限；未來校準值須同時通過兩端驗證，不能只靠Web能顯示。
- catalog.master.scale現在為1，兩端目前都沒有使用此欄位；有效倍率是clip.scale。不要把未實作的master.scale當新全局調節器。
- 後續尺度標準應使用可見眼線／面部與中性身體landmark，帽子／道具另留安全區；不能拿同N畫布、總bbox或相同scale宣告本體一致。每段仍只允許一個固定倍率，禁止逐幀fit。
- 紀錄每個clip的原圖/regions/catalog SHA、播放來源格、有效每像素倍率和實際viewport。只有更新後的真尺寸review與原生重建結果能證明下一版。
